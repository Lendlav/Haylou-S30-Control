# SPP-протокол HAYLOU S30

Документ описывает только команды, подтверждённые анализом клиентского кода и предыдущими проверками на наушниках. Формат произвольных или OTA-команд не описан намеренно.

## Транспорт

- Bluetooth Classic RFCOMM / SPP endpoint: UUID `0000FD3D-0000-1000-8000-00805F9B34FB`.
- Android открывает UUID напрямую. Linux находит RFCOMM channel по SDP-записи именно `FD3D`.
- `1101` — стандартный UUID Serial Port Profile, но прежнее соединение по нему не давало ответа управления S30.
- Сопряжение делается штатными средствами ОС. Приложения не сканируют эфир и не выполняют pairing.

## Внешний кадр

```text
AA BB CC | type | opcode | length_hi | length_lo | sequence | payload... | DD EE FF
```

Длина — big-endian и включает `sequence` вместе с payload, но не включает заголовок и конечную метку. В исходящем запросе type = `C0`; sequence меняется на каждый запрос. Ответы проверяются на допустимый тип, opcode, sequence и статус.

Успешная ANC-команда может иметь ответ такого вида:

```text
AA BB CC 00 08 00 02 00 00 DD EE FF
```

Внешний кадр в клиентском протоколе не содержит выявленных прикладных CRC, MAC или подписи. Это не вывод о шифровании Bluetooth link: радиообмен отдельно не захватывали.

## Подтверждённые команды

### ANC / прозрачность

Opcode `08`, payload `02 04 <mode>`:

| Mode | Режим | Полный кадр |
| ---: | --- | --- |
| `00` | Обычный, ANC выключен | `AA BB CC C0 08 00 04 00 02 04 00 DD EE FF` |
| `01` | Шумоподавление | `AA BB CC C0 08 00 04 00 02 04 01 DD EE FF` |
| `02` | Прозрачность | `AA BB CC C0 08 00 04 00 02 04 02 DD EE FF` |

### Встроенный EQ

Opcode `F2` (установка конфигурации устройства), config ID `07`, payload `03 00 07 <preset>`:

| Preset | Название | Пример кадра |
| ---: | --- | --- |
| `00` | Стандартный | `AA BB CC C0 F2 00 05 00 03 00 07 00 DD EE FF` |
| `01` | Вокал | — |
| `02` | Рок | `AA BB CC C0 F2 00 05 00 03 00 07 02 DD EE FF` |
| `03` | Классика | — |
| `04` | Поп | — |
| `05` | Бас | — |
| `06` | Саббас | — |
| `07` | Мягкий | — |
| `08` | Улица | — |

Остальные коды имеют тот же кадр, последний байт заменяется кодом пресета. Границы `0–8` подтверждены обычным экраном выбора звука производителя и поведением приложения.

## Ошибочная команда EQ из тестового экрана

Во внутреннем тестовом экране официального Android APK обнаружен `0x08` с payload `02 02 <mode>`. Он может получать ACK, но не соответствует штатному пути пресетов. Обычный экран вызывает `BtDeviceEqSettingRequest`, который отправляет `0xF2` / config `7`. Это объяснило прежний симптом «команда принята, звук не меняется».

Произвольный EQ передавался бы отдельным режимом (код `15`), который гарнитура отклоняет. В обоих проектах такого UI и передачи нет.

## Что не следует выводить из vendor APK

Библиотека перечисляет множество opcode (информация, reboot, уведомления телефона, EDR, runtime status, unbind, передача файлов, функции/конфигурация и пр.). Это лишь наличие обработчика в приложении. Без конкретного успешного ответа S30 нельзя считать команду поддерживаемой или безопасной. В этом исследовании неизвестные команды не отправлялись.

## Поведение приложений

- Ubuntu: SDP discovery по UUID `FD3D`; команда ANC/EQ ждёт и сопоставляет ответ. Звук регулируется системным PipeWire/PulseAudio sink через `pactl`.
- Android: RFCOMM socket по UUID `FD3D`; ANC/EQ отправляются из foreground service. Громкость меняет media stream телефона. Lock-screen controls используют MediaSession.
- Успешный ACK сам по себе не является измерением акустического эффекта. Проверяйте фактический звук при безопасной громкости.
