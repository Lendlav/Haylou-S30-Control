# Самостоятельное исследование HAYLOU S30 с нуля

Гайд сохраняет уже найденный безопасный путь исследования. Он не содержит инструкций по отправке неизвестных команд или прошивке модифицированного образа.

## 1. Подготовить рабочие материалы

1. Создайте отдельную папку проекта и записывайте туда исходники, заметки и контрольные суммы.
2. Не помещайте в Git производственный APK, распакованный/decompiled APK, firmware, pairing databases, Bluetooth captures, ключи подписи, MAC/serial identifiers или логи, содержащие их.
3. Сначала изучайте клиентскую логику и публичные документы. Помечайте каждое утверждение как подтверждённое устройством, найденное в клиенте или гипотезу по SDK.
4. Для приложений сравнивайте только исходники. Их сборки создают `build/`; каталоги исключены Git.

## 2. Управление через SPP

1. Сопрягите HAYLOU S30 обычным системным Bluetooth UI.
2. Найдите SPP UUID `0000FD3D-0000-1000-8000-00805F9B34FB`. На Linux изучите SDP record для этого UUID и возьмите RFCOMM channel из записи; не подставляйте стандартный UUID `1101` или фиксированный канал.
3. Сначала проверьте только известную ANC-команду: `0x08`, payload `02 04 <mode 00..02>`. Сопоставьте ответ по sequence и status.
4. Для EQ используйте штатный путь: `0xF2`, config ID `7`, preset `0..8`. Не используйте похожий payload из тестового экрана и не считайте ACK доказательством звукового результата.
5. Начинайте с низкой громкости, меняйте за раз одну настройку и фиксируйте результат. Подробный формат и кадры: [PROTOCOL.md](PROTOCOL.md).

Приложения в репозитории реализуют рабочий подтверждённый набор. Для Android сначала проверьте разрешения Bluetooth и настройки показа MediaSession controls на экране блокировки. Для Ubuntu используйте сборочные шаги из [Linux README](../apps/linux/README.md).

## 3. Исследование официального Android-клиента

1. Получите приложение только из официального магазина/источника. Его анализировать можно офлайн на локальной копии.
2. Найдите реализацию подключения, UUID, сборщик пакета, запрос основного экрана EQ и OTA flow. Отличайте экран от внутренних тестовых/диагностических экранов.
3. Не отправляйте неиспользованные enum команды устройству только потому, что они есть в APK.
4. Не публикуйте APK, извлечённые классы/ресурсы или крупные фрагменты кода производителя. Публикуйте собственное краткое описание наблюдений и ссылки на официальный источник.

В ходе этого исследования выяснилось, что официальный клиент проверяет MD5 скачанного firmware package и инициирует OTA. Кнопку обновления нельзя использовать как «скачать файл для анализа»: она начинает обновление.

## 4. Исследование низкого заряда и firmware

1. Пока не установлен документированный способ получить оригинальный firmware package без старта OTA, ограничьтесь публикациями и SDK.
2. Открытый SDK Jieli — только пример для платформенного семейства. Сверьте board, SoC, конфигурацию и прошивку конкретной гарнитуры до любых выводов.
3. Для сигнала батареи ищите отдельно warning tone и low-voltage shutdown. Исследовательская цель может касаться только звукового предупреждения; порог/защиту батареи сохранять.
4. Если появится штатный firmware package, сначала копируйте оригинал в локальный каталог вне Git, вычисляйте SHA-256 и делайте статический анализ копии. Ничего не устанавливайте.
5. К модификации переходить только после подтверждения формата образа, подписи, recovery и наличия проверенного оригинального дампа. Без надёжного восстановления остановиться до аппаратной записи.

## 5. Аппаратные документы

1. Сверьте полное оглавление FCC отчёта и страницы внутреннего фото. Текущая локальная копия отчёта неполная.
2. Используйте обзоры 52audio как сведения о семействе чипов и других изделиях, но не копируйте по ним распиновку в S30.
3. Не подавать напряжение и не подключать программатор к неизвестным площадкам. Требуются точная идентификация площадок, электрические уровни, схема питания, схема восстановления и безопасная процедура размыкания питания.

## 6. Что записывать в журнал

Для каждого эксперимента фиксируйте дату, аппаратную/программную версию без персональных идентификаторов, точное известное действие, ожидаемое поведение, фактическое поведение и способ проверки. Отдельно отмечайте, менялся ли звук фактически или был лишь ACK. Не храните пароли, MAC, серийный номер, pairing files или сырые радиозаписи в публикуемой папке.
